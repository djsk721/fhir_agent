# 연구계획서

**연구 제목:** 로컬 LLM과 FHIR 스키마 검색을 활용한 Conversion Profile 자동 생성 및 검증 기반 보정

## 1. 연구 배경과 목적

병원 데이터베이스의 정보를 HL7 FHIR로 변환하려면 원천 필드의 의미, 자료형, 코드 체계, 단위, 시간, 환자·입원 간 참조를 함께 해석해야 한다. 정형 임상데이터에 LLM과 스키마 검색을 적용해 FHIR 매핑을 지원한 선행 연구가 있다. 본 연구에서는 로컬 LLM이 생성한 매핑 규칙을 재사용하고, 검증 피드백으로 규칙을 보정하는 방법을 평가한다. 핵심 질문은 표준 검사 오류를 줄이면서도 새 환자의 원천 값과 참조 관계를 보존할 수 있는가이다. [정형 임상데이터 FHIR 변환 선행 연구](https://arxiv.org/abs/2507.03067) · [HL7 FHIR R4 규격](https://hl7.org/fhir/R4/)

데이터 조회는 검토된 읽기 전용 Extractor가 수행한다. LLM의 동적 SQL 생성, 데이터베이스 탐색과 조회 계획 보정은 연구 범위에서 제외한다. 같은 환자의 같은 원천 레코드를 모든 비교군에 제공해, 조회 차이가 변환 품질 차이로 해석되는 것을 방지한다.

목표 산출물은 실행 가능한 변환 명세, 변환 및 검증 절차, 그리고 변환 방식·보정·검색의 기여를 분리해서 보여 주는 환자 단위 평가 결과다. 모델 추론은 통제된 로컬 환경에서 수행하며, 각 실험에서 실제로 사용한 외부 의존성을 기록한다.

## 2. 연구 질문

1. **매핑과 실행 가능성:** 원천 메타데이터와 FHIR 규격을 바탕으로 의미가 올바르고 결정적 변환 모듈에서 실행할 수 있는 Conversion Profile을 생성할 수 있는가? Profile의 생성 성공, 실행 가능 여부, 독립 정답 매핑과의 일치를 구분해서 측정한다.
2. **변환 방식의 차이:** 동일 원천 입력에서 Hybrid 방식과 LLM 직접 생성 방식의 원천 충실도, FHIR 적합성, 변환 완전성 및 처리 시간에 어떤 차이가 있는가?
3. **보정의 효과:** 초기 Profile을 검증 피드백으로 보정하면, 독립 평가 환자에서 새 오류나 원천 정보 손실을 늘리지 않으면서 오류를 줄일 수 있는가?
4. **보조 분석 — 스키마 적용성과 검색의 기여:** MIMIC에서 확정한 생성·보정 절차를 다른 스키마인 Synthea에도 적용할 수 있는가? 동일한 FHIR 근거에 원천 스키마 벡터 검색을 추가하면 결과가 달라지는가?

## 3. 연구 자료와 고정 환자 집합

| 구분 | 원천 입력과 독립 참조 | 역할 |
| --- | --- | --- |
| MIMIC | MIMIC-IV v2.2의 관계형 원천 데이터와 MIMIC-IV on FHIR v2.1의 대응 기록 | 개발·검증·내부 평가의 주 자료. 소규모 기능 확인에는 별도 Demo 코호트를 사용하고 전체 자료 결과와 구분한다. |
| Synthea | 같은 생성 실행에서 출력한 CSV와 FHIR R4 | 스키마가 다른 합성 보조 자료. CSV에서 직접 추출한다. 동일 로직의 적용성을 평가하며 실제 타 기관 자료로 일반화하지 않는다. |

평가 리소스는 **Patient, Encounter, Condition, Observation** 네 종류로 고정한다. 모든 분석 범위에는 선택된 환자의 대상 입원과 실제 추출 명세에 포함된 대상 이벤트를 포함한다. MIMIC의 FHIR 참조는 같은 원천 계열을 별도로 변환한 산출물이다. 원천 입력에 없는 파생값·확장·리소스는 임상 값의 정답 일치율 평가에서 제외하고, 평가 대상과 제외 근거를 기록한다. Synthea의 FHIR 참조도 원천 CSV와 비교 가능한 범위를 미리 정한다. [MIMIC-IV v2.2](https://physionet.org/content/mimiciv/2.2/) · [MIMIC-IV on FHIR v2.1](https://physionet.org/content/mimic-iv-fhir/2.1/) · [Synthea, Walonoski 등](https://pubmed.ncbi.nlm.nih.gov/29025144/)

MIMIC은 개발·검증·평가, Synthea는 적응용 준비·평가 역할을 환자 단위로 분리한다. 한 환자의 사건을 서로 다른 역할에 흩어 배정하지 않는다. 소규모 반복 검증은 두 데이터셋에서 **각각 미리 정한 소수 환자**만 사용한다. 환자별 원천 데이터와 분할은 로컬의 코호트 파일 및 해시로 관리한다. 동일 코호트로 재실행할 때 해시를 검사하고, 환자·역할·원천 자료가 달라지면 새 코호트로 기록한다. 코드나 논문 본문에는 환자 식별자 목록을 넣지 않는다.

이미 오류를 관찰하고 기준을 조정한 환자는 개발 파일럿에 속한다. 본평가에는 이들과 중복되지 않는 환자를 사전에 확정한다. Synthea는 생성기 버전, seed, 기준일, 사용 모듈, CSV·FHIR 출력 옵션을 기록한다. MIMIC의 원천 및 파생 자료는 접근이 통제된 환경에서 사용하고, 데이터 이용 조건과 소속 기관의 심의 절차를 확인한 뒤 본실험을 진행한다.

## 4. 변환 방법과 비교군

1. 검토된 추출 명세로 대상 레코드와 원천 메타데이터를 준비한다. 입력 수와 누락 여부를 남긴다.
2. Mapping Agent는 환자 예시 행 없이, 허용된 원천 스키마와 FHIR R4 규격에서 Conversion Profile을 생성한다. 원천 스키마와 FHIR 정의는 별도 인덱스에서 검색한다. 필수 FHIR 제약과 원천 키 관계는 정확 조회로도 전달한다. Profile은 필드, 자료형, `value[x]`, 코드·단위, 날짜·시간, 식별자와 Reference의 변환 규칙을 포함한다.
3. 검증된 Profile을 공통 Renderer가 실행한다. 변환 중 발생한 오류와 누락은 원천 행과 함께 추적한다.
4. 초기 결과의 JSON Schema 및 HL7 FHIR Validator 오류와 사전에 정한 원천 값 보존 검사 결과를 준비 자료에서 확인한다. 정해진 보정 한도 내에서 Profile을 수정한 뒤 다시 실행한다. 독립 참조 FHIR 및 정답 매핑은 생성·검색·보정에 사용하지 않고 평가에만 사용한다.
5. MIMIC 개발 단계에서 모델과 버전, 프롬프트, 검색 방법·임베딩, FHIR 인덱스, 변환 코드, 검증기와 보정 한도를 고정한다. Synthea에는 원천 스키마 인덱스만 별도로 구축하고 같은 방법으로 Synthea용 Profile을 새로 생성한다.

| 비교군 | 평가 환자에 적용하는 방식 | 주요 비교 |
| --- | --- | --- |
| B1 · Direct | 동일 원천 입력에서 LLM이 FHIR JSON을 직접 생성 | B1과 P1로 변환 방식의 차이를 평가 |
| P1 · Hybrid | 초기 Profile을 고정하고 Renderer만 실행 | P1과 P2로 Profile 보정의 효과를 평가 |
| P2 · Hybrid + Correction | 준비 환자에서 보정한 Profile을 고정하고 Renderer만 실행 | P1·P2 각각에서 FHIR-only와 이중 RAG 비교 |

원천 RAG 비교는 모델·프롬프트·FHIR 근거·정확 조회와 환자 입력을 동일하게 유지한다. 사람이 작성한 추출 명세와 데이터셋별 원천 보존 검사 항목을 기록한다. 운영 파이프라인의 기존 FHIR export 결과는 별도의 개발 참고 자료로만 사용한다. [이중 RAG 베이스라인](./dual_rag_baseline.md)

## 5. 평가와 분석

주 평가 지표는 **MIMIC 평가 환자별 독립 참조 대비 원천 필드 정확도**로 둔다. 이 값은 대상 이벤트가 누락되거나 정확히 연결되지 않는 경우도 반영한다. 보정 효과는 표준 오류와 참조 오류의 감소, 새 오류와 누락 여부를 함께 보고 판단한다. RQ1의 매핑 품질과 실행 가능성은 독립적으로 보고한다.

| 평가 영역 | 측정 방법 |
| --- | --- |
| 매핑 품질과 실행 | 독립 정답 매핑과의 필드·자료형·참조 규칙 일치. 표현이 다른 규칙의 의미상 동등성 인정 기준을 사전 정의. 생성 실패와 Renderer 실행 실패는 별도 집계. |
| 표준 적합성 | 실제 HL7 Validator의 error/fatal과 Bundle 통과율. 전체 시도 대비 통과율과 생성된 Bundle의 통과율을 구분. 용어 서버와 적용한 FHIR 버전·프로파일 범위를 기록. |
| 원천 충실도 | 전체 평가 범위를 분모로 한 필드 정확도와, 매칭된 이벤트에서의 코드·값·단위·시간 등 필드 정확도를 함께 보고. 참조가 없는 항목은 미평가로 분리. |
| 완전성과 참조 | 예상 행 대비 누락·과생성, 이벤트 매칭률과 Precision/Recall/F1. 필요한 참조의 생성 여부와 생성된 참조의 해소·대상 일치 여부를 구분. |
| 보정 효과 | 해결된 오류와 새 오류를 함께 집계. 오류 건수가 줄어든 경우, 모든 준비 검사를 통과한 경우, 독립 평가 환자의 품질이 향상된 경우를 분리. |
| 처리 효율 | Profile 생성·보정의 일회성 비용과 평가 환자 변환 비용을 분리. 호출 수, 토큰, 경과 시간과 처리량을 보고. 로컬 GPU 사용을 API 과금으로 환산하지 않음. |

비교 전에 MIMIC의 시간대 없는 원천 시각을 해석하는 기준과 환자·입원 업무 키, Synthea 단일 검사와 패널 구성요소의 대응 범위, 검사값의 숫자·문자 자료형 처리를 고정한다. 기준을 적용하기 어려운 사례와 제외 규모도 보고한다. 누락된 리소스나 참조를 점수 개선을 위해 평가 범위에서 사후 제거하지 않는다. 정답 매핑은 예측 Profile과 독립적으로 준비하고, 작성 근거를 남긴다.

주 분석에서는 환자별 점수의 대응 차이와 환자 단위 재표집에 따른 95% 신뢰구간을 보고한다. 한 환자의 반복 관측을 독립 표본으로 세지 않는다. 확대 파일럿에서 환자별 차이의 분산, 환자 내 상관성, 리소스별 표본 수와 실패 빈도를 점검한 다음, 주 분석에서 필요한 정밀도 또는 검정력을 기준으로 최종 환자 수를 정한다. 소수 고정 코호트 실험은 재현성과 실패 유형 확인을 위한 것으로, 효과 크기나 일반화의 확정 근거로 사용하지 않는다.

## 6. 진행 현황과 본실험 착수 조건

2026년 11월 20일 GPU 개발 파일럿에서는 MIMIC Demo 평가 환자 1명과 Synthea 평가 환자 2명에서 세 비교군이 실행됐다. RAG를 사용한 MIMIC에서 초기 Hybrid 대비 보정 Hybrid의 HL7 오류는 68건에서 2건으로 감소했지만 독립 참조 필드 정확도는 10.54%로 같았고, Synthea는 오류 263건에서 50건, 필드 정확도 56.39%에서 63.36%로 바뀌었다. 보정 Hybrid에서 두 자료 모두 통과한 환자 Bundle은 없었다. 해당 파일럿은 Encounter 누락, 문자형 Observation 누락과 참조 불일치를 확인하는 데 활용한다. 독립 정답 매핑 평가는 이 파일럿 범위에 포함되지 않았다. [실행 및 검증 기록](./research_verification.md)

2026년 11월 21일에는 같은 환자 역할을 고정하고 읽기 전용 추출·참조 해시를 확인했다. MIMIC Demo는 준비 1명·평가 1명, Synthea는 준비 1명·평가 2명이다. 개선된 숫자·문자 분기와 업무키 참조, 비교 이벤트 기준을 적용하고 원천 의미에서 별도로 작성한 부분 매핑 참조를 사용해 평가 경로를 확인했다. 이 코호트를 보고 보완한 규칙은 새로 고정한 평가 환자에서 검증한다. [고정 환자 검증 보고서](./fixed_pilot_report.md)

본실험에 앞서 다음 조건을 점검한다.

1. **평가 계약 확정:** 정답 매핑, 비교 가능 필드, 시각·패널·참조 정렬, 대상 분모, 검증기 적용 범위를 문서화한다.
2. **소규모 고정 코호트 검증:** MIMIC과 Synthea에서 별도의 고정 환자 집합을 사용해 누락·참조·자료형 회귀 검사를 수행하고 환자 집합과 원천 입력의 동일성을 확인한다. 모델을 새로 실행한 결과, 저장된 Profile 재실행과 테스트 결과를 구분해 기록한다.
3. **정책 잠금과 독립 평가:** 확대 파일럿 결과에 따라 표본과 분석 기준을 확정한다. 새 평가 환자를 분리한 뒤 MIMIC B1/P1/P2와 RAG 대응 비교를 수행한다. 고정 정책으로 Synthea에서 재현하고 합성 자료로서의 한계를 보고한다.

구현과 실행 절차는 [연구 프로토콜](./research_protocol.md)에, 실제 실행 범위와 한계는 [검증 기록](./research_verification.md)에 정리한다.
